# BUSMASTER 프로그램 분석 해설

> 이 문서는 `ARCHITECTURE.md`(구조 참조서)의 companion이다.
> 구조가 "무엇으로 되어 있나"를 다룬다면, 이 문서는
> **"프로그램이 실제로 어떻게 동작하나"를 이야기 형식으로 해설**한다.
> Python 포팅을 할 때 각 장면이 어떻게 바뀌는지도 함께 적었다.

---

## 프롤로그 — 이 프로그램은 뭐하는 건가

자동차 안에는 수십 개의 전자제어장치(ECU)가 CAN이라는 통신선으로 서로 대화한다.
"브레이크 밟아", "속도 60km/h", "엔진 온도 90도" 같은 메시지들이
초당 수천 개씩 오간다. 엔지니어는 이 대화를 **들여다보고, 기록하고,
가짜 메시지를 쏘아보며** ECU를 테스트해야 한다.

BUSMASTER가 바로 그 일을 하는 프로그램이다. 쉽게 말하면
**CAN/LIN 통신용 오실로스코프 + 녹음기 + 가상 대화 상대**다.

- **보기**: 버스 위를 오가는 메시지를 실시간으로 표시
- **기록**: 로그 파일로 저장 (나중에 재생 가능)
- **말 걸기**: 원하는 메시지를 직접 만들어서 버스에 전송
- **해석**: DBC 데이터베이스를 이용해 날 것(raw)의 바이트를 "속도=60" 같은 의미로 번역
- ** 흉내내기**: 실제 ECU 없이 가상 노드가 대화에 참여 (NodeSim)

## 제1장 — 실행부터 종료까지의 여정

프로그램을 켜서 끄기까지, 큰 흐름은 이렇다.

```
1. 실행        BUSMASTER.exe 시작, MFC 메인 프레임 생성
2. 드라이버 선택  어떤 하드웨어로 버스에 붙을지 선택 (Vector? PEAK? Kvaser?)
3. DB 로드      DBC 파일을 읽어 메시지/시그널 정의 적재
4. 연결         드라이버 DLL 로드 → 채널 연결 → 버스 참여
5. 송수신       메시지 주고받기 (Rx 표시, Tx 전송, SignalWatch 해석)
6. 기록/재생    로그 저장, 필요하면 리플레이
7. 종료         연결 해제, DB 메모리 해제
```

각 장면을 자세히 들여다보자.

## 제2장 — 장면별 해설

### 장면 1. "DBC 파일이 프로그램 속으로 들어오는 과정"

**등장**: DBC 파일 → `DBC2DBFConverter` → `CMsgSignal`

DBC는 "이 차에서 오가는 메시지들의 사전"이다. 텍스트 파일이라 사람이 읽을 수 있지만,
BUSMASTER는 이걸 그대로 쓰지 않는다. 내부용 이진 포맷(DBF)으로 한 번 변환한다.

1. 사용자가 DBC 파일을 지정한다.
2. `DBC2DBFConverter`가 lex/yacc 기반 파서(`dbc_dbf_Lexer.l`)로 DBC를 읽는다.
   메시지 정의(`BO_`), 시그널 정의(`SG_`), 값 설명(`VAL_`) 등을 파싱한다.
3. 파싱 결과가 `sMESSAGE`/`sSIGNALS` 구조체들의 연결 리스트로 메모리에 올라간다.
4. `CMsgSignal`이 이 리스트를 품는다. 이후 프로그램 전체가
   "ID 0x123이면 속도 메시지, 3번 비트부터 12비트가 속도 시그널" 같은 지식을
   `CMsgSignal`에게 물어본다 (`psGetMessagePointer()`).

**핵심 포인트**: DBC 파싱은 한 번만 일어나고, 결과는 메모리의 연결 리스트 DB가 된다.
`CMsgSignal`은 이 프로그램의 "사전" 역할을 하는 싱글톤에 가까운 존재다.

**Python 포팅**: `bsmaster/dbc/parser.py`가 DBC 텍스트를 직접 읽어
`DbMessage`/`DbSignal` 객체로 만든다. 중간 DBF 단계를 둘 필요가 없다 —
Python에서는 파싱 결과를 바로 객체로 들고 있으면 되니까, 구조가 더 단순해진다.

### 장면 2. "CAN 프레임 하나가 화면에 찍히기까지" (수신 경로)

**등장**: 하드웨어 → 드라이버 DLL → `CMsgWndThread` → 메시지 창

1. CAN 하드웨어가 프레임을 받으면, 벤더 드라이버 DLL이 DIL 규약에 맞춰
   `STCAN_MSG` 구조체로 바꿔서 올린다.
2. `CMsgWndThread`(수신 전용 스레드)가 이 프레임을 받아낸다.
   UI 스레드와 분리되어 있는 이유는, 초당 수천 개씩 쏟아지는 메시지가
   화면 그리기를 막지 않게 하기 위해서다.
3. 메시지 창의 컨테이너(`CMsgContainerBase`)에 프레임이 쌓인다.
4. 화면에는 ID, DLC, 데이터 바이트, 타임스탬프가 한 줄로 표시된다.
5. SignalWatch가 켜져 있으면, `CMsgSignal` DB를 뒤져서
   "이 ID의 몇 번 비트가 무슨 시그널이더라"를 찾아내고,
   날 바이트를 물리값으로 번역해서 보여준다.

**핵심 포인트**: 수신은 **생산자(DLL)→큐→소비자(UI 스레드)** 구조다.
이 분리 덕분에 버스가 바빠도 화면이 얼지 않는다.

**Python 포팅**: `queue.Queue` + 스레딩(또는 asyncio)으로 같은 구조를 만든다.
PySide6의 시그널/슬롯이 스레드 간 전달을 담당한다.

### 장면 3. "버튼 하나로 메시지를 쏘는 과정" (송신 경로 + 시그널 인코딩)

**등장**: TXWindow → `CMsgSignal` → `sSIGNALS::vSetSignalValue()` → DIL → 하드웨어

1. 사용자가 TX 창에서 "ID 0x200 메시지의 속도 시그널을 60으로" 입력한다.
2. `CMsgSignal`에서 해당 메시지의 `sSIGNALS` 정의를 가져온다.
   (시작 바이트, 시작 비트, 길이, 엔디안, factor/offset)
3. `vSetSignalValue()`가 마법을 부린다:
   - 값을 시그널 비트 길이로 마스킹 (`60 & ((1<<12)-1)`)
   - Intel(리틀엔디안)이면 `(startByte-1)*8 + startBit` 만큼 시프트해서
     8바이트 데이터 위에 정확히 얹는다
   - Motorola(빅엔디안)이면 바이트 순서를 뒤집어가며 배치한다
   - 기존 데이터에서 해당 시그널 비트만 지우고(`un64GetBitMask()`),
     새 값을 OR로 합성한다
4. 완성된 8바이트가 `STCAN_MSG`에 담겨 DIL을 거쳐 드라이버로,
   드라이버에서 실제 CAN 버스로 나간다.

**핵심 포인트**: 시그널 인코딩은 **비트 단위 수술**이다.
엔디안에 따라 비트 배치 규칙이 완전히 다르며, 이 로직이 틀리면
ECU가 엉뚱한 값을 받는다. 포팅에서 가장 정밀도가 요구되는 부분이다.

**Python 포팅**: `encode_signal()` / `decode_signal()` 함수로 구현하고,
원본 C++ 로직과 비트 단위로 동일한 결과를 내는지 테스트로 검증한다.
(Python의 임의 정밀도 정수는 64비트 마스킹 연산에 오히려 유리하다.)

### 장면 4. "로그 파일이 만들어지는 과정"

**등장**: FrameProcessor (`CBaseLogObject`)

1. 사용자가 로깅을 켜면 `CBaseFrameProcessor_CAN`이 로그 객체를 만든다.
2. 수신되는 모든 프레임이 로그 객체에 복제되어 흘러간다.
   (화면 표시와 독립적인 경로라, 화면이 버벅여도 기록은 된다.)
3. 설정된 포맷(ASC/BLF 등)에 맞춰 파일에 쓴다.
4. 나중에 `Replay`로 이 파일을 다시 읽어 "그때 그 버스 상황"을 재현한다.

**핵심 포인트**: 로깅은 **관찰자 패턴**이다. 송수신 본류에 영향을 주지 않고
옆에서 복사해 간다.

**Python 포팅**: 로그 기록기를 제너레이터/컨텍스트 매니저 기반으로 설계하면
C++보다 훨씬 간결해진다. 포맷별 writer를 플러그인식으로 둔다.

### 장면 5. "필터가 메시지를 걸러내는 과정"

**등장**: Filter DLL

1. 사용자가 "ID 0x100~0x200만 보여줘" 같은 필터를 설정한다.
2. Filter DLL이 조건식을 받아서, 수신 경로 중간에 끼어든다.
3. 조건에 맞는 프레임만 메시지 창으로 통과시킨다.

**핵심 포인트**: 필터는 Rx 경로의 **게이트키퍼**다.
원본은 별도 DLL이지만, Python에서는 그냥 함수 체인으로 구현하면 된다.

## 제3장 — 등장인물(클래스) 소개

| 인물 | 본명 (C++) | 성격 | Python 분신 |
|------|-----------|------|-------------|
| 프레임 | `STCAN_MSG` | 말단 병사. ID+데이터 8바이트를 들고 뛰어다닌다 | `CanFrame` ✅ |
| 사전 | `CMsgSignal` | 박학다식. 모든 메시지/시그널 정의를 외우고 있다 | `MessageDatabase` (예정) |
| 시그널 정의서 | `sSIGNALS` | 설계도. "몇 번 비트부터 몇 비트가 무슨 뜻"을 적어둠 | `DbSignal` (예정) |
| 메시지 정의서 | `sMESSAGE` | 시그널 정의서들을 묶은 한 권의 문서 | `DbMessage` (예정) |
| 통역사 | `sINTERPRETSIGNALINFO` | 날 바이트를 "속도 60km/h"로 번역해줌 | `InterpretedSignal` (예정) |
| 인코더 | `sSIGNALS::vSetSignalValue` | 비트 수술 전문의 | `encode_signal` (예정) |
| 수신 담당 | `CMsgWndThread` | 쉴 새 없이 프레임을 받아내는 일꾼 | 스레드+큐 (예정) |
| 기록 담당 | `CBaseLogObject` | 옆에서 조용히 받아적는 서기 | 로그 writer (예정) |
| 문지기 | Filter DLL | 조건에 안 맞는 프레임은 통과시키지 않음 | 필터 함수 체인 (예정) |
| 운전기사들 | `CAN_Vector_XL` 등 DLL | 실제 하드웨어를 모는 기사들. 각자 다른 회사 소속 | 이식 제외 (시뮬레이션 모드로 대체) |
| 만능 해결사 | `Utility/` | 여기저기 불려다니는 잡역부 | 필요시 선별 이식 |

## 제4장 — Python으로 옮기면 어떻게 바뀌나 (관점 정리)

| 원본의 모습 | Python에서의 모습 | 이유 |
|------------|------------------|------|
| 연결 리스트 (`sSIGNALS* m_psNext`) | `list[DbSignal]` | GC가 메모리 관리를 해주니 수동 연결 리스트 불필요 |
| `CMap<UINT, sMESSAGE*>` | `dict[int, DbMessage]` | 표준 dict가 더 빠르고 간결 |
| `SIG_VALUE` 공용체 | 그냥 `int` | 임의 정밀도라 오버플로 걱정 없음 |
| `CString` | `str` | — |
| MFC 다이얼로그 (`.rc`) | PySide6 위젯 (코드로 작성) | `.rc` 리소스는 버리고 새로 설계 |
| 스레드 + 윈도우 메시지 | `QThread` + 시그널/슬롯 (또는 `queue`) | Qt 방식이 더 안전 |
| DLL 플러그인 (DIL) | Python 모듈/클래스 | import가 곧 플러그인 로딩 |
| lex/yacc DBC 파서 | 직접 작성한 파서 | 중간 DBF 단계 생략 가능 |

**한 줄 요약**: C++의 "수동 메모리 + 플러그인 DLL + MFC" 구조가
Python에서는 "객체 + 모듈 + Qt" 구조로 바뀌며, 전체 코드량은 크게 줄어든다.
단, **비트 단위 인코딩 로직과 DBC 문법만큼은 원본과 동일해야** 하므로
이 두 부분은 테스트로 엄격히 검증한다.

## 부록 — 용어집

| 용어 | 설명 |
|------|------|
| CAN | 자동차용 시리얼 통신 규격. 두 가닥 선으로 여러 ECU가 대화 |
| LIN | CAN보다 저속·저가형 서브 네트워크용 규격 |
| DBC | CAN 메시지/시그널 정의 파일 (텍스트). "차량의 통신 사전" |
| DBF | BUSMASTER 내부용 이진 DB 포맷 (DBC를 변환한 것) |
| DIL | Driver Interface Layer. 드라이버 DLL들의 공통 규약 |
| DLC | Data Length Code. 프레임의 데이터 바이트 수 |
| ECU | Electronic Control Unit. 자동차의 전자제어장치 |
| ID | 메시지 식별자 (11비트 표준 / 29비트 확장) |
| Signal | 메시지 안에 들어있는 개별 값 (예: 속도, 온도) |
| Intel/Motorola | 시그널 바이트 순서. 리틀엔디안/빅엔디안에 대응 |
| PGN | J1939에서의 메시지 그룹 번호 |
| UDS | 차량 진단용 상위 프로토콜 |
| NodeSim | 가상 ECU를 띄워 실제처럼 대화시키는 기능 |
| STUB 드라이버 | 하드웨어 없이 동작하는 가짜 드라이버 |
